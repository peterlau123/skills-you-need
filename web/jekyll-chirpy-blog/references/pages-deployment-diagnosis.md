# GitHub Pages Deployment Diagnosis — Session 2026-08-18

## Context

After PR #119 (mermaid fix for Bifrost post) was merged to `main` (commit
`999ead4`), all CI workflows showed green but the post URL returned 404.

## Investigation path

### 1. CI status — all green

Checked Actions API for `peterlau123/peterlau123.github.io`:
- Markdown Lint: completed/success
- Site Validation: completed/success
- Deploy Jekyll site to Pages: completed/success
- pages build and deployment (legacy Pages): completed/success

Pages build latest: `status: "built"`, `error.message: null`, commit `999ead4`.

All build steps verified via `/actions/runs/<id>/jobs`:
- `build` job: all 10 steps success (checkout → Ruby → bundle install →
  Jekyll build → verify output → upload artifact)
- `deploy` job: all 3 steps success (setup → deploy-pages → complete)

### 2. Live URL — all 404

```
/posts/bifrost-agent-architecture/         → 404
/2026/08/05/bifrost-agent-architecture/      → 404
/bifrost-agent-architecture/                 → 404
/sitemap.xml                                 → 404 (GitHub Pages 404 page)
/feed.xml                                    → 404 (GitHub Pages 404 page)
/                                            → 200, but only 34 bytes
```

The 34-byte homepage body was `---\nlayout: home\n# Index page\n---` —
this is the **raw index.html frontmatter**, not rendered HTML. Jekyll
was not processing anything.

### 3. Root cause — dual deployment conflict

**Pages API** (`GET /pages`):
```json
{
  "status": "built",
  "build_type": "legacy",      // ← serves raw files from branch
  "source": { "branch": "main", "path": "/" }
}
```

**`.nojekyll` file** exists at repo root (added 2025-12-13 in commit
`9ce8c7d`, message: "fix: fix Jekyll site 404 errors by committing built site").
Under legacy mode, `.nojekyll` tells GitHub Pages to skip Jekyll entirely
and serve raw files. So `_posts/*.md` are never rendered to HTML.

**Actions workflow** (`.github/workflows/jekyll.yml`):
- Triggers on push to main
- Builds with `bundle exec jekyll build`
- Deploys via `actions/deploy-pages@v4` (uploads artifact, creates deployment)

**The conflict**: Both systems run on push to main:
1. Actions workflow: builds Jekyll → uploads artifact → `deploy-pages` →
   deployment status `success`
2. Legacy Pages builder: serves raw branch files → creates a second
   deployment → marks the Actions deployment as `inactive` (superseded)

**Deployments API** showed two deployments for commit `999ead4`:
- `5965117511` (14:43:37Z): queued → in_progress → **success** (14:49:14Z)
- `5965125235` (14:44:01Z): queued → in_progress → success → **inactive**
  (14:49:15Z, superseded)

The legacy builder's deployment (which serves raw files) won.

### 4. Fix attempt — API 403

```bash
curl -X PUT -H "Authorization: token $GITHUB_TOKEN" \
  -d '{"build_type":"workflow"}' \
  "https://api.github.com/repos/peterlau123/peterlau123.github.io/pages"
# → 403 "Resource not accessible by personal access token"
```

The fine-grained PAT has `contents:write` but not Pages admin permission.
Fix requires user action in GitHub UI:

**Settings → Pages → Build and deployment → Source → "GitHub Actions"**

## Key lessons

1. **"CI green" ≠ "site deployed correctly"** — when Pages has a legacy
   builder + Actions workflow both running, the legacy builder can silently
   overwrite the Actions artifact.

2. **`.nojekyll` + `build_type: legacy` = no Jekyll** — the file disables
   Jekyll processing under legacy Pages mode. If you also have a Jekyll
   Actions workflow, you have a conflict.

3. **Homepage returning tiny raw frontmatter** (34 bytes of `---\nlayout:
   home\n---`) is a tell-tale sign that Jekyll didn't run. A working Jekyll
   site returns full HTML (kilobytes, with `<html>`, `<head>`, etc.).

4. **sitemap.xml and feed.xml 404** — these are generated by Jekyll. If
   they're 404, Jekyll didn't build, regardless of what CI says.

5. **Two deployments for same commit with `inactive` status** — the
   superseded deployment was the Actions workflow's. The active one is
   the legacy builder's raw-file serving.

6. **`gh` CLI not installed** — all GitHub API checks via `curl` + REST API
   with `GITHUB_TOKEN` from `~/.hermes/.env`.

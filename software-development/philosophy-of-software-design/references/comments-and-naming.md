# 注释与命名（第 12-14 章）

## 一、注释：描述代码中不明显的内容

### 四个借口（都被反驳）

| 借口 | 反驳 |
|---|---|
| "好代码自文档化" | 代码无法表达设计意图（为什么、规则、约束、权衡） |
| "没时间写" | 延迟 = 永远不写；写注释是投资 |
| "注释会过时" | 过时是因为写得不规范，不是注释本身的问题 |
| "见过的注释都没用" | 那是烂注释；好注释描述不明显的内容 |

### 黄金法则

> **注释应提供代码本身无法表达的信息**：为什么、规则、权衡、抽象。
> 反模式：注释重复代码（Comment Repeats Code）——注释内容从代码立即可见。

### 注释类型与粒度

| 类型 | 位置 | 内容 |
|---|---|---|
| **接口注释** | 类/方法/函数声明前 | 整体抽象、行为、参数、返回值、副作用、异常、调用前提 |
| **数据结构成员注释** | 字段声明旁 | 字段含义、不变量 |
| **实现注释** | 复杂逻辑内 | 为什么用这种方式、复杂的局部逻辑 |

- 接口注释（抽象层）：比代码**更高层**——描述"调用后会发生什么"
- 实现注释：比代码**更低层**——描述代码内部细节
- 反模式：实现文档污染接口（接口注释描述用户不需要的实现细节）

### 注释先行（第 15 章）

把写注释放在**设计过程的开头**，而非代码完成后：

1. 新类：先写类接口注释
2. 最重要的公共方法：写接口注释 + 签名，方法体留空
3. 迭代注释直到结构正确
4. 写实例变量声明 + 注释
5. 填方法体，需要时补充实现注释

好处：注释成为设计过程的一部分 → 更好的文档 + 更好的设计。
迟到的注释是烂注释：记忆模糊、重复代码、缺失最重要信息。

## 二、命名：精确 + 一致（第 14 章）

### 为什么重要

> 真实案例：Sprite OS 用 `block` 变量同时表示物理块号和逻辑块号 → 数据损坏 bug，修了 6 个月。
> 读者看到 `block` 是物理块号就反射性假设它真的是——**名字制造了思维盲区**。

### 命名标准

- **精确**：在读者脑海中创建图像——是什么，**不是什么**
- 好名字本身就是抽象：聚焦最重要的属性，省略次要细节
- 孤立测试：看到名字（不看声明/文档/用法），能猜出它指什么吗？
- 太长 → 笨拙；太泛 → 无信息（`data`、`info`、`temp` 都是红旗）
- **难以取名 = 设计问题的信号**（实体职责不清）

### 一致性（第 17 章）

- 一致性创造**认知杠杆**：学会一处 → 立即理解其他处
- 不一致 = 每个情况单独学 + 误导性假设 → 错误
- 一致性层次：命名、编码风格、接口、设计模式、**不变量**
- 不变量：总是为真的属性 → 减少特例、便于推理

## 三、写代码时的检查清单

- [ ] 每个公共接口都有接口注释？描述"做什么"而非"怎么做"？
- [ ] 注释是否提供了代码本身无法表达的信息（为什么/规则/权衡）？
- [ ] 有没有注释在重复代码？（有则删）
- [ ] 每个名字都能通过孤立测试？有没有 `data`/`info`/`temp` 类名字？
- [ ] 难以取名的地方？→ 停下来，可能职责不清
- [ ] 相似事物是否用相似方式命名/实现？（一致性）

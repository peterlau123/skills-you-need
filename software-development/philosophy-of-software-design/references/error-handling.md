# 错误处理哲学：把错误定义掉（第 10 章）

> 异常处理是软件系统中**最糟糕的复杂性来源之一**。处理特殊情况的代码本质上比处理正常情况更难写。
> 核心目标：**减少必须处理异常的地方的数量**。

## 为什么异常昂贵

1. 异常路径代码比正常路径难写
2. 每个抛出点都是调用者的认知负担（每个调用者都要处理）
3. 嵌套异常传播使代码难以阅读
4. 开发者常在不考虑"如何处理"时就定义异常

## 四种技术（按优先级）

| 技术 | 做法 | 例子 |
|---|---|---|
| **1. 消除异常** | 改变操作语义，让正常行为覆盖所有情况 | 删除不存在的文件返回 OK 而非报错 |
| **2. 异常屏蔽** | 低层处理异常，不向上抛 | TCP 协议层内部重传，上层只看到可靠字节流 |
| **3. 异常聚合** | 批量操作把多个异常聚合成一个 | `PartialFailureException` 携带所有失败项 |
| **4. 崩溃 vs 处理** | 无法合理处理的异常直接 fail fast | 内部状态不一致 → 崩溃，别让调用者背着 |

## 反模式（把复杂性往上推）

- ❌ 不确定怎么处理就抛异常让调用者处理 → **每个调用者都要处理**（1 个问题变 N 个）
- ❌ 不确定策略就导出配置参数 → **每个系统管理员都要学习**（如缓存大小、重试次数）

## 决策问题清单

设计错误处理时逐项检查：

1. 这个异常**真的需要存在吗**？能否改变语义消除它？
2. 这个异常**应该由谁处理**？低层能屏蔽吗？
3. 这个异常**会不会成为调用者的常态负担**？批量场景能聚合吗？
4. 这个情况**值得恢复吗**？还是崩溃更诚实？
5. 特殊返回值代替异常？⚠️ 调用者容易忘记检查，谨慎使用

## 与"把复杂性往下压"的联系

错误处理是把复杂性往下压的典型场景：**模块的接口简单 > 模块的实现简单**。
开发者承担异常处理 = 一次；让每个调用者处理 = N 次。多数模块用户多于开发者，所以开发者受苦更划算。

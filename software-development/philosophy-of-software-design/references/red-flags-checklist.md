# 危险信号检查表（评审用）

> 配合 `code-review` skill 使用：作为 Standards 轴的补充输入，或独立快速评审。
> 逐项扫描代码，发现信号 → 定位 → 说明违反了哪条原则 → 给出重构建议。

## 模块结构

- [ ] **浅模块**：接口不比实现简单？→ 增加接口抽象度，隐藏更多实现细节
- [ ] **信息泄漏**：一个设计决策反映在多个模块？→ 把决策收进单一模块
- [ ] **时间分解**：结构基于执行顺序而非信息隐藏？→ 按知识/职责重组
- [ ] **过度暴露**：API 强迫调用者为常用功能了解不常用功能？→ 拆分接口，隐藏低频功能
- [ ] **透传方法**：方法只是把参数传给签名相似的另一方法？→ 删中间层/加深低层接口/合并层
- [ ] **重复**：非平凡代码反复出现？→ 提取共享形状
- [ ] **特殊-通用混合**：专用代码未与通用代码分离？→ 拆分
- [ ] **联合方法**：两方法依赖太强，不理解一个就无法理解另一个？→ 合并或重新划分职责

## 注释

- [ ] **注释重复代码**：注释内容从代码立即可见？→ 删除，改为描述不明显信息
- [ ] **实现文档污染接口**：接口注释描述用户不需要的实现细节？→ 移到实现注释
- [ ] 接口注释缺失或只描述"怎么做"？→ 补"做什么 + 前提 + 副作用"

## 命名

- [ ] **含糊名称**：名字无法传达有用信息（data/info/temp）？→ 精确化
- [ ] **难以取名**：为实体找不到精确直观的名字？→ 设计问题的信号，检查职责
- [ ] **难以描述**：完整文档必须很长？→ 通常意味着实体承担了太多职责

## 代码可读性

- [ ] **非显而易见代码**：行为/含义不易理解？→ 简化、加注释、选好名字
- [ ] 变更放大：简单修改需要碰多处？→ 收集到同一模块
- [ ] 认知负荷：完成任务需要读大量不相关代码？→ 拆浅模块为深模块

## 评审输出格式

```
## 发现
- [信号名] `文件:行号` — 违反原则 + 具体证据
- [信号名] `文件:行号` — ...

## 重构建议
1. ...（针对最高优先级的 1-2 个问题）
2. ...

## 总结
X 个信号，最严重的是：...
```

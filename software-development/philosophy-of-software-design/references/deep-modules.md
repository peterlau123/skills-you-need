# 深模块指南（第 4-9 章）

> ⚠️ 词汇表对齐：深模块相关术语（seam/adapter/leverage/locality）以 `codebase-design` skill 为准，本文件只补充 APoSD 的原则与判断标准，不重复建设词汇。

## 深模块 vs 浅模块

```
深模块:  小接口 + 大实现（好）      浅模块:  接口与实现几乎一样大（坏）
  接口  ←—— 简单                       接口 ←—— 与实现一样复杂
  ┌──────────────┐                    ┌──────────────┐
  │ 实现（复杂逻辑│ ←—— 隐藏复杂性      │ 实现（很简单） │ ←—— 隐藏不了任何东西
  └──────────────┘                    └──────────────┘
```

- **深模块**：接口很小、实现承担大量复杂工作 → 用户只面对一小部分复杂性
- **浅模块**：接口不比实现简单 → 没起到封装作用
- 评价标准：**接口应该设计得让最常见的用法最简单**（不是最通用的用法）

## 信息隐藏（创造深模块最重要的技术）

- 每个模块封装一些"设计决策"知识，藏在实现里，不出现在接口中
- 接口只描述**做什么**，不描述**怎么做**
- 违反信息隐藏 = **信息泄漏（Information Leakage）**：一个设计决策反映在多个模块中

### 反模式：时间分解
- 代码结构基于**操作执行顺序**而非信息隐藏 → 一个功能的知识散落在多个"阶段"模块中
- 典型例子：读文件→处理→写文件，拆成三个模块

## 通用模块更深（第 6 章）

- **"有点通用"（somewhat general-purpose）**：功能反映当前需求，但**接口不绑定**当前需求
- 接口够通用以支持多种用途，但不过度设计到难以使用
- 通用方法的最大好处：**接口更简单更深**（即使只用于一个用途也值得）

## 分层与抽象（第 7 章）

- 不同层应提供**不同抽象**；相邻层抽象相似 = 危险信号
- 反模式：**透传方法（Pass-Through Method）**——方法除了把参数传给签名相似的另一个方法外几乎不做任何事
  - 危害：认知负荷 + 接口膨胀 + 层间无抽象变化
  - 解决：让低层接口更丰富（deep）、或合并层、或拆出中间层共享接口

## 把复杂性往下压（第 8 章）

- 原则：**模块的接口简单 > 模块的实现简单**
- 多数模块用户多于开发者 → 让开发者受苦，别让用户受苦
- 反模式：抛异常让调用者处理（每个调用者都要处理）；导出配置参数（每个管理员都要学习）
- 正例：编辑器文本类用字符接口（实现复杂但上层简单）vs 行接口（实现简单但上层每次 split/join）

## 合并还是分开（第 9 章）

细分成本：组件数量增加、接口增多、分离带来认知负担、可能重复。

**相关的代码放一起**：
- 共享信息（如都依赖同一文档语法）
- 一起使用（双向强关联；单向关联如"块缓存总用哈希表"不算）

**通用 vs 专用分离**：通用机制（如哈希表）与专用逻辑（如块缓存）分开。

## 设计两次（第 11 章）

- 每个主要设计决策考虑**多个根本不同的方案**，即使确信只有一个合理方案也强制考虑第二个
- 列出每个方案的优缺点，最重要的考量是**对上层软件的易用性**
- 还要考虑：接口更简单？更通用？实现更高效？

## 修改现有代码（第 16 章）

- **保持战略性**：不要"最小改动"心态（= 战术编程，让设计恶化）
- 每次修改后，系统应该具有"从一开始就考虑这个变化"的结构
- 每次改代码时，至少让设计变好一点点；没变好 = 在变坏
- 投资心态：10-20% 时间用于清理和重构，长期回报

## 设计时的检查清单

- [ ] 模块接口 vs 实现：接口真的比实现简单吗？（深 vs 浅）
- [ ] 有没有设计决策泄漏到多个模块？（信息泄漏）
- [ ] 有没有透传方法？（只转发参数的中间层）
- [ ] 接口绑定当前需求了吗？能否更通用但不难用？
- [ ] 有没有把复杂性推给调用者？（异常、配置参数）
- [ ] 相关代码在一起吗？通用/专用分离了吗？
- [ ] 至少考虑过 2 个不同的设计方案吗？
